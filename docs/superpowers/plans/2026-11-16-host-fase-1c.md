# Host Ordenen (fase 1c) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The post is visible in the web interface, lands in an inbox, moves to a person's name and gets labels: by hand, on a proposal (name matching, a rule, the AI choosing from the workspace's own lists) or automatically by a rule, with every change in the document's history and undoable; rules are built and tested on a tab "Automatisering"; tasks can be listed and ticked off.

**Architecture:** Three new Django apps: `people` (persons, name matching), `labels` (labels, presets) and `rules` (a pure engine, an executor, preset rules). `documents` gains the links (`DocumentAddressee`, `DocumentLabel`), one table for every proposal (`DocumentSuggestion`) and the history (`DocumentEvent`); one service, `documents.organise`, is the only code that changes a document's labels and addressees. The pipeline's extraction call carries the closed lists of persons and labels as short aliases and its last step stores suggestions and runs the rules. The web gets workspace routes (inbox, post, document, persons, labels, automations) on the existing React stack.

**Tech Stack:** As in 1b (Python 3.13, Django 6.1, Django Ninja, PostgreSQL 18 with forced RLS, Procrastinate, pytest; React 19, TanStack Router and Query, React Aria Components, Lingui, Vitest, MSW). No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-16-fase-1c-ordenen-design.md` (the design; section numbers below as "D 6.2"). Background: `docs/SPEC.md` sections 7–10, 12–14. Previous plan: `docs/superpowers/plans/2026-11-14-host-fase-1b.md`. iOS counterpart: `../Brievie_ios/docs/superpowers/plans/2026-11-16-ios-fase-1c.md`.

## Global Constraints

- Everything in `CLAUDE.md` and the Global Constraints of the 1a and 1b plans holds: English code, Dutch B1 text through `gettext` (backend) and Lingui `t` macros (web, then `pnpm extract`); UUID `id` + `created_at` + `updated_at`; `mypy --strict`, `ruff` clean, no `Any`, no bare `except`; thin endpoints calling one service function wrapped in `transaction.atomic`; error body `{"code", "message"}` via `ApiError`; no document text, names, label names, tokens or BSNs in logs.
- Every new table subclasses `WorkspaceModel`, lists its workspace foreign keys in `same_workspace_fields`, and its first migration ends with `enable_rls(<table>)`. `tests/test_rls_coverage.py` passes unchanged.
- The API is additive under `/api/v1`. Every operation has the camelCase `operation_id` named in the design, typed schemas, and documents its error responses (`AUTH_ERRORS`, `SESSION_WRITE_ERRORS`, `BODY_ERRORS` as the existing endpoints do). Nullable fields are primitives only; nullable inputs have a default; the contract test (no `anyOf`) passes. Input schemas derive from `InputSchema`.
- The 1b app must keep working: no existing field changes meaning, `confirmDocument` without the new fields behaves as before.
- Text typed by a user (person names, variants, label names, rule names and values) goes through `mask_bsns` before it is stored.
- Jobs take ids only, enter `workspace_context` themselves, in short transactions; none is open during the AI call.
- Only ids from the workspace's own lists are ever stored as a label or addressee proposal (D 10.2). Nothing automatic repeats a change the user dismissed on that document (D 8).
- Web: the CSP is not changed. No inline styles, no blob URLs; page images are `<img>` on the API endpoint; label colours are CSS classes. Every page has a title (`usePageTitle`), works by keyboard, and tests query by role.
- After every API change: `make openapi`, `cd web && pnpm gen:api`, commit both generated files with the change.
- Work on branch `feat/fase-1c`, branched from `main`. Conventional commits, trailer `Co-Authored-By: Claude <noreply@anthropic.com>`. Do not push. iCloud creates conflict copies with " 2" or " 3" in the name: never commit one; when a build breaks oddly, look for them first and move them aside.

## Review Focus

1. The AI returns a label or person id that is not in the list it was given (an invented one, one from an earlier request, the same one twice): nothing is stored for it and no label or person is created. → Task 9 (`test_unknown_alias_is_dropped`), Task 10 (`test_ai_pick_of_deleted_label_is_skipped`).
2. The user takes off a label that a rule put on, and later the rules run again (confirm, or "toepassen op bestaande post"): the label stays off. → Task 8 (`test_removing_by_hand_marks_dismissed`), Task 12 (`test_dismissed_change_is_never_reapplied`).
3. A confirm is sent twice because the answer got lost, and between the two an automatic rule added a label: the second answers 200 with the same document, not 409. → Task 12 (`test_repeated_confirm_after_auto_rule_is_200`).
4. A short or common name ("Jan" in "januari", a two-letter variant, a name inside a longer surname) must not put a letter on somebody's name. → Task 7.
5. A preset rule that fires on nearly every letter (a word from a letterhead) makes labels meaningless on day one. → Task 12 (`test_presets_on_sample_letters`).
